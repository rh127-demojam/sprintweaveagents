CPAT - Cloud Platform Automation Tool

Web-based application for automated registration and deployment of RHOSO (Red Hat OpenStack Services on OpenShift) on an existing RHOCP cluster.

Built and maintained by SprintWeave AI agents that analyze RHOSO documentation, generate CIQ input files, and scaffold the complete CPAT application source code.

Version: tag/API YY.M.W (e.g. 26.7.4); UI displays vYY.M.W (e.g. v26.7.4)

For product scope, installation task details, CIQ parameters, and playbook examples, see USAGE.md.

SprintWeave Agents

Three AI agents collaborate to design, generate, and deploy RHOSO automation artifacts. Agent definitions live under .cursor/rules/ and activate automatically based on user prompts.

Agent Rule File Role
Orchestrator agent-orchestrator.md Pipeline coordinator — sequences agents, enforces gates, reports progress. Never generates artifacts directly.
RHOSO DA (Design Architect) agent-rhoso-da.md Analyzes RHOSO documentation and project artifacts to produce CIQ workbooks, schema code, lab requirements, EDPM topology guides, and PDF gap matrices.
RHOSO Deployment Engineer agent-rhoso-deployment-engineer.md Scaffolds or enhances CPAT source code (Ansible roles, Flask backend, React frontend, Docker), generates manifest catalogs, workflow MoPs, and deployment task briefs.

Pipelines

Pipelines chain agents into ordered stages. Definitions are stored in two files that the Orchestrator merges at runtime:

File Purpose
tools/pipelines-default.yaml Built-in pipeline definitions (canonical)
context/pipelines.yaml Team customizations, promoted pipelines, deletions

How to Trigger a Pipeline

Pipelines are triggered by typing the pipeline command in the Cursor chat, or by clicking Launch on the CPAT Dashboard canvas.

Run RHOSO delivery pipeline on @cpat

The Orchestrator agent activates, resolves the matching pipeline, announces the execution plan, and runs each stage sequentially.

Pipeline Management Commands

Command Action
Manage pipelines List all pipelines with status
Create pipeline Guided custom pipeline creation
Edit pipeline [name] Modify an existing pipeline
Restore default pipelines Reset context/pipelines.yaml to defaults

Gates (Quality Checkpoints)

Gates are configurable pause points between pipeline stages. When enabled, the Orchestrator stops after each agent completes and waits for user approval before proceeding.

Gate configuration lives in context/team-config.yaml:

gates:
  enabled: true
  mode: pause-approve
  apply_to: pipeline          # pipeline | all
  checklist:
    require_source_traceability: true
    require_pii_clean: true
    require_no_unverified: true
    require_min_items: true
  skip_agents: []

Gate Behavior

Setting Effect
enabled: true Gates are active for pipelines
enabled: false All stages run without pausing
apply_to: pipeline Gates apply only during pipeline execution
apply_to: all Gates apply to every agent invocation

Gate Responses

At each checkpoint the user can respond with:

Response Action
approve / next / continue Proceed to the next stage
approve all Disable gates for remaining stages
skip Skip current gate (marked as "skipped")
reject: [reason] Re-run the agent with the feedback

Overriding Gates in Prompts

  • Add "with gates" or "with checklist" to force gates ON
  • Add "no gates" to force gates OFF
Run RHOSO delivery pipeline on @cpat with gates
Run RHOSO DA pipeline on @cpat no gates

RHOSO Install Workflow (CPAT UI)

  1. Generate Manifests for Review — render YAML from CIQ into artifacts/<cluster>/ (no oc apply).
  2. Review — view or download manifests in the RHOSO Installation page. Download All (ZIP) packages all manifests into <cluster>-manifests.zip.
  3. Deploy — select tasks; template-based tasks apply the reviewed files by default. Optional Re-render templates before apply regenerates then applies.

API: POST /api/rhoso-installations/run with execution_mode = generate | deploy | full, and optional re_render_manifests.

Running CPAT

Using the bring-up script

From the output/cpat/ directory:

chmod +x bringup.sh
./bringup.sh

Other commands:

./bringup.sh --build     # build image only (also prunes intermediate images)
./bringup.sh --restart   # stop, rebuild, and start
./bringup.sh --stop      # stop and remove container
./bringup.sh --help      # show all options

Open http://localhost

Local Development (without containers)

Backend:

cd output/cpat/backend
python -m venv venv
venv\Scripts\activate        # Windows
pip install -r requirements.txt
python app.py

Frontend:

cd output/cpat/frontend
npm install
npm run dev

Open http://localhost:5173

Versioning (YY.M.W)

CPAT uses calendar versioning YY.M.W for image tags, env, and API:

Part Meaning
YY Two-digit year
M Month without leading zero for 1–9
W Week of the month (1–5): days 1–7 → 1, 8–14 → 2, etc.
  • Backend: output/cpat/backend/version.py
  • Override: set environment variable CPAT_VERSION

Data Storage

All runtime state is stored outside the CPAT application source at output/cpat/data/ (created dynamically by paths.py):

Content Local path Container path
SQLite DB data/cpat.db /cpat-data/cpat.db
CIQ uploads data/uploads/ /cpat-data/uploads/
Input secrets data/secrets/<cluster-id>/ /cpat-data/secrets/<cluster-id>/
Registration logs data/logs/registrations/ /cpat-data/logs/registrations/
Installation logs data/logs/installations/ /cpat-data/logs/installations/
Generated manifests data/artifacts/<cluster>/ /cpat-data/artifacts/<cluster>/

Data is ephemeral — lost when the container is removed. bringup.sh does not mount a host volume.
